Architectural Blueprint

Multimodal Inference Platform on EKS

This is the reference design I would work toward for IFM: one GitOps-managed EKS platform serving LLM, TTS, and ASR models behind OpenAI-compatible endpoints, with observability and cost controls built in from the start.

1. Registry CI/CD
  • Checkpoints versioned in S3 + MLflow registry
  • GitHub Actions builds and scans serving images
  • Smoke eval (latency, quality) gates promotion
  • Terraform owns VPC, EKS, IAM, RDS
2. Deploy Helm + ArgoCD
  • One Helm chart per engine, values per model
  • ArgoCD syncs dev → staging → prod
  • GPU node pools by class (H100 / L4 / CPU)
  • Canary rollout with automatic rollback
3. Serve vLLM / SGLang
  • LLMs on vLLM or SGLang with tensor parallelism
  • ASR (Whisper) and TTS on right-sized GPUs
  • OpenAI-compatible gateway with auth & quotas
  • Autoscaling on queue depth and KV-cache use
4. Use & Observe Grafana
  • OpenWebUI and Gradio demos for users
  • Prometheus: TTFT, tokens/s, GPU utilization
  • CloudWatch + alerting on SLO burn
  • Per-model GPU cost dashboards

GitOps Repository Layout

Infrastructure, charts, and per-model configuration stay separate, so adding a new model to the cluster is a reviewed values file rather than a new pipeline:

infra/ ├── terraform/ # VPC, EKS, GPU node groups, IAM (IRSA), RDS, S3 charts/ ├── llm-serving/ # vLLM / SGLang Deployment, HPA, PDB, ServiceMonitor ├── speech-serving/ # ASR + TTS workers with GPU requests and probes └── gateway/ # OpenAI-compatible routing, auth, rate limits deploy/ ├── argocd/ # ApplicationSets per environment └── models/ ├── llm-chat.values.yaml ├── asr-whisper.values.yaml └── tts.values.yaml
Technical Interview Q&A

How I Would Answer the Likely Questions

These are the questions I expect for a senior MLOps role on a foundation-model inference team, with answers grounded in systems I have run.

Q1

Walk us through a model you took from fine-tuned checkpoint to production serving. What broke, and what did you change?

Kimi-Audio for domain-specific voice tasks: I fine-tuned the open-source audio foundation model with LoRA/SFT, served it with vLLM on GPU instances, and put Prometheus/Grafana monitoring on the serving path.

Serving Choices

vLLM for continuous batching and paged KV-cache, which gave far higher throughput than naive per-request generation, with LoRA adapters kept separate from the base weights.

Operating It

Diagnosed and resolved serving performance issues across multiple deep-learning models on serverless GPUs, and gated GPU access for the team through Coder workspaces.

Takeaway for IFM

Treat each model as config on a shared platform: same image pipeline, same metrics, same rollout path, whichever engine serves it.

Q2

How would you choose between vLLM, SGLang, and TensorRT-LLM for a new model?

I measure first rather than pick on reputation. I have run vLLM and Triton in production, and I would put SGLang and TensorRT-LLM through the same harness.

Benchmark on Real Traffic Shape

Replay representative prompt/output lengths and concurrency; compare TTFT, inter-token latency, tokens/s per GPU, and cost per million tokens.

Weigh Operational Cost

vLLM and SGLang load Hugging Face weights directly and suit fast-moving research checkpoints. TensorRT-LLM needs an engine build step, which pays off for stable, high-traffic models.

Workload Fit

SGLang's prefix caching suits multi-turn chat and agent traffic with shared prefixes; quantization (FP8/AWQ) is evaluated against a quality eval, not only speed.

Q3

How do you design CI/CD for ML models, not just services?

At Walleye Capital and US Biolab I built GitHub Actions pipelines that automated testing, training, and promotion: workflow dispatches submitted Vertex AI Pipelines on GCP and started on-demand EC2 runners for training and hyperparameter tuning on AWS.

Version Everything

Code, data snapshots, model artifacts, and serving config each have their own version, tracked in MLflow, so any deployment can be reproduced.

Gate on Evals

A model is promoted only after passing a quality eval and a load test; I bring this from designing graders for frontier-agent RL tasks.

Deploy Declaratively

CI writes a new image tag or values file; GitOps applies it. Rollback means reverting a commit.

Q4

GPU inference costs are rising. Where do you look first?

Utilization before hardware. Most GPU spend I have seen is idle or badly batched capacity rather than a lack of compute.

Measure per Model

Prometheus + Grafana dashboards for GPU utilization, KV-cache occupancy, and cost per request, broken down by model and team.

Batch What Can Wait

At Walleye, moving async LLM calls to batch inference cut token costs by 50%. The same idea applies to offline ASR/TTS jobs on spot capacity.

Right-Size and Scale to Zero

Match small TTS/ASR models to smaller GPUs, scale idle research endpoints to zero, and reserve large GPUs for LLMs that need tensor parallelism.

Q5

Your Kubernetes experience is mostly Kubeflow and Airflow on K8s. How would you ramp on Helm, ArgoCD, and EKS?

The concepts are ones I already use; the tools are what's new. Kubeflow pipelines are Kubernetes resources, so pods, resource requests, node selection, and service accounts are familiar. Terraform and Pulumi taught me to keep infrastructure declarative and reviewed.

Learn on the Real System

Read IFM's existing charts and ArgoCD apps first, then ship a small change end-to-end in week one.

Use Agentic Tooling

I use Claude Code daily to read unfamiliar codebases, draft charts, and triage failures quickly, always verifying the output myself before it ships.
