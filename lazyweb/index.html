How I read the brief

I am not pitching a generic backend resume. I read Lazyweb as two loops that should share one contract: a research loop that already exists, and a runtime loop that the first engineer is being hired to industrialize.

The company, as I understand it

An AI-native growth and experimentation company: an opinionated layer on open-source experimentation tooling, plus proprietary pipelines, reporting, and workflow logic. Today that shows up as TypeScript and Python SDKs, an MCP server, and a companion web app. The customer center of gravity is mobile. The public surface — screens, flows, and experiment evidence served to agents — only works if the data underneath is trustworthy.

That matches what Ali has practiced for years at Duolingo: experiment hygiene is not a slide. It is the product. A first engineer who treats assignment, exposure, and reporting as one system will compound faster than someone who only ships SDK wrappers.

What the first hire actually owns

  • Extend the backend that assignment, targeting, and config already live on.
  • Design the SDK contract, then ship mobile clients (iOS, Android, React Native / Flutter) against it.
  • Own treatment logic, statistical reporting, and the pipelines that make both honest.
  • Integrate third-party and open-source experimentation tools instead of rebuilding the universe.
  • Make architecture calls with the founding team, in writing, at early-stage speed.

How I would operate

01

Hygiene over features

A wrong assignment log is worse than a missing chart. Guardrails ship with the pipeline, not after the first bad call.

02

One contract, many SDKs

Python and TypeScript stay the reference. Mobile clients implement the same spec — types, retries, sticky bucketing, versioned events.

03

Warehouse before streams

At this stage, correct ELT and a metric tree beat a premature event bus. Introduce streaming when latency actually demands it.

04

Fail safe on the client

Mobile networks lie. SDKs cache assignment, batch exposures, and never block the UI on a stats round-trip.

90-day plan

A first hire should create leverage, not a rewrite. I would keep the current TypeScript and Python SDKs as the source of truth, make the data honest, then grow mobile clients off one spec. Dates assume we pick the first mobile target from the actual customer mix in week one.

Days 1 – 30 · absorb and stabilize

Make the current system legible

  • Map MCP, web app, TS/Python SDKs, and the open-source experimentation core. Write a short architecture note, not a wiki novel.
  • Inventory the event taxonomy. Separate assignment, exposure, and conversion. Find where they currently collapse into one blob.
  • Stand up warehouse models for experiment reporting on whatever is already there (BigQuery or equivalent).
  • Ship one user-visible reliability fix in production so I am in the loop before I propose bigger moves.

Exit: a shared RFC, a metric tree, and a backlog the founders can argue with.

Days 31 – 60 · contract and first mobile SDK

Lock the spec, then ship a client

  • Publish a language-agnostic SDK contract (OpenAPI or equivalent): init, assignment, exposure, config refresh, identity.
  • Add contract tests against the existing TypeScript SDK so mobile cannot drift.
  • Ship the first mobile SDK — React Native if that covers most customers, native iOS if it does not. Thin. Documented. Versioned.
  • Client behavior: sticky bucketing, local cache, request timeouts, batched events, fail-open vs fail-closed made explicit per flag type.

Exit: one mobile app can assign, emit, and show up in a report.

Days 61 – 90 · reporting that can be trusted

Close the loop to the agent surface

  • Automated experiment reporting: lift, intervals, sample-ratio mismatch, and guardrail metrics.
  • Wire those results into MCP tools and the web app so agents and humans see the same numbers.
  • Data-quality monitors on volume, schema drift, and identity joins — the boring work that keeps hygiene real.
  • Playbook for Android / Flutter as copies of the same contract, not new designs.

Exit: a repeatable path from SDK event to a decision, without a founder in the SQL.

Week one, specifically

I would not start by rewriting the stack. I would pair on a live customer or internal integration, read the assignment path end to end, and leave with three artifacts: the current event dictionary, the first mobile target, and a list of “this will lie to us” issues ranked by blast radius. Founders should feel progress in the first seven days, not just a discovery deck.

SDK design I would not compromise on

  • Spec first OpenAPI (or proto) generated types. Python and TypeScript remain the reference implementations the contract tests run against.
  • Tiny mobile footprint No analytics kitchen sink. Assignment + config + batched events. Battery and privacy constraints are part of the design, not a later ticket.
  • Identity that survives app restarts Anonymous ID, optional logged-in merge, and a written rule for what happens when those disagree — or reports will lie.
  • Versioned payloads Schema evolution with additive fields. Old clients stay valid. That is how you ship iOS, then Android, without freezing the backend.

Tradeoffs I would bring to the table

  • RN vs native first Choose from the customer list, not from resume preference. One well-instrumented client beats three half SDKs.
  • Warehouse-first vs stream-first Start with scheduled transforms unless assignment/config latency or volume forces a bus. I have built both; I will not fashion a Kafka cluster for its own sake.
  • Extend OSS, do not fork it Proprietary logic belongs in pipelines, policy, and reporting. Forking the experimentation core is how a three-person company inherits a fourth product.
  • Frontend stays out of scope I will consume the web app as a customer of the API. I will not quietly become the frontend owner.
